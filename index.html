The runtime for long-lived agents.

Norns keeps an agent's state in an append-only event log and dispatches one step at a time to workers you run. The orchestrator never calls a model or executes a tool. A run survives the loss of any worker, a deploy, or a restart of the orchestrator itself.

System

Orchestrator and workers

The orchestrator is an Elixir application in front of Postgres. It holds agent definitions, conversations and the event log, runs one process per live agent, and decides what happens next. It never calls a model and never runs a tool.

Workers are your code, in your network, holding your keys. A worker connects over a WebSocket, says what it can do, and receives one task at a time in a provider-neutral JSON format. That is the whole contract, so a worker can be written in whatever language the job calls for: a Python worker for the model and data tools, a Go or Rust worker where a sandbox or a binary matters, an Elixir worker when it is already a Phoenix app. SDKs ship for Python and Elixir; the protocol is documented for the rest.

When a worker goes away, the work it held is handed to the next one. When none is available, it waits.

Durability

State lives in the log, not the process

Every step of an agent run is written to a durable log in Postgres. Agents restore their state by replaying the log. A crashed process restarts exactly where it was, and completed steps are never run again. A run can wait on a timer, a person, or another agent for as long as it takes.

Delivery is at-least-once with duplicate suppression. Tool calls that have side effects carry an idempotency key.
