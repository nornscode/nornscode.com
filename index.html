A durable runtime for LLM agents.

Norns keeps an agent's state in an append-only event log and dispatches one step at a time to workers you run. The orchestrator never calls a model or executes a tool. A run survives the loss of any worker, a deploy, or a restart of the orchestrator itself.

runtime
Elixir on BEAM/OTP, one process per agent
state
PostgreSQL, versioned events, rebuilt on resume
workers
WebSocket, llm and tools capabilities, provider-neutral tasks
delivery
at-least-once, duplicates suppressed by idempotency key
deployment
single node; multi-node is on the roadmap

01System

Orchestrator and workers

The orchestrator is a state machine over an event log. Workers are your code, in your network, holding your API keys. The split is the whole design: anything that can fail or leak lives on the worker side, and anything that must survive lives on the orchestrator side. 

orchestrator  (Elixir, Postgres)            worker  (your process, your keys)
      │                                        │
      │  llm_task  {model, messages, tools} ──▶ │  calls the LLM provider
      │ ◀── tool_result  {content, usage} ──────│
      │  append llm_response                   │
      │  tool_task  {task_id, name, input} ───▶ │  runs the tool
      │ ◀── tool_result  {result | error} ──────│
      │  append tool_result, checkpoint        │
      │                                        ╳  worker lost
      │  re-dispatch held tasks with the same
      │  task_id and idempotency key; with no
      │  worker available, queue                │  next worker registers
      │  tool_task  {same task_id, input} ────▶ │  runs it, or reports tool_duplicate
      │ ◀── tool_result ────────────────────────│
orchestratorholds

Agent definitions, conversations, and the run event log, all in Postgres. Each live agent is one BEAM process under a DynamicSupervisor, started on the first message and stopped when idle. Message content is opaque to it: routing is on roles, tool names, ids, steps and usage, never on the text the model sees.

orchestratordoes not hold

Provider API keys, tool implementations, or a network path to anything the tools reach. It cannot call a model. With no worker connected, tasks queue and the run waits.

workerregisters

Over a WebSocket on /worker, with a worker id, capabilities (llm, tools), the tools it serves with their JSON input schemas, and optional protocol features. Tasks are pushed in a provider-neutral format; the worker translates to Anthropic, OpenAI, or whatever it uses.

workerleaves

A clean shutdown sends drain, finishes its in-flight tasks, and disconnects. A worker that just drops has the tasks it held re-dispatched to any matching worker, or to the queue. Three attempts in total: a task that outlives three workers is reported to the agent rather than dispatched a fourth time.

workerasleep

A serverless worker declares its tools and a wake URL up front. When a task arrives with no connected worker, the orchestrator POSTs a signed wake to that URL, the platform starts the worker, and it connects like any other.

02Agent process

States

The process is never blocked. It answers status queries in every state, and the state is derived from the log, so a crashed process comes back in the state it left.

A run parked on a question re-parks on the same question after a restart, because the pause is re-derived from the still pending ask_human call. The run JSON carries status: "waiting" and a waiting_for object, so a client can tell working from waiting without reading the log.

modes
taskeach message starts a fresh run with no history. Default.
conversationmessages append to a persistent conversation keyed by an external id, such as a Slack channel. One agent serves many conversations concurrently, each one process. A sliding window with a compaction summary bounds context growth.
built-in tools, resolved by the orchestrator
waitpark until a timer fires
ask_humanpark until a human answers; delivered by run webhook
launch_agentstart a child run; authorized server-side by allowlist and max_depth, every decision logged. A resumed parent reattaches to its in-flight child instead of launching it again.
list_agentsenumerate agents the policy allows the caller to see

A worker cannot shadow a built-in; dispatch resolves these first. Everything else is a worker tool.

03Worker protocol

On the wire

Workers join worker:lobby with a registration and then receive task pushes. The format is provider-neutral; the reference implementations are the Python and Elixir SDKs.

messages
directioneventpayload
server → workerllm_taskmodel, system_prompt, summary, date, messages or messages_delta, tools, context_policy
worker → servertool_resulttask_id, status, content or tool_calls, finish_reason, usage, model, final_output
server → workertool_tasktask_id, tool_name, input
worker → servertool_resulttask_id, status, result or error
worker → serverdrainstop dispatching; in-flight tasks finish, then the worker leaves
worker → serverregister_portinternal_port, name, protocol, url. Gard workers only.

A worker that joined with message_cache keeps the last message list it was sent per run and receives messages_delta: {base_count, drop, append} on later steps instead of the full history. A miss is answered with message_cache_miss and the full list is resent at the same step without counting a retry. Unknown feature names are ignored, so a newer SDK joins an older core.

04Event log

What is recorded

Every event is validated against a schema before it is written and carries schema_version: 1. Run state is a fold over this table. Resume, fork, cost, and the run summary all read from it and nothing else.

delivery guarantee

At-least-once with duplicate suppression. A side-effecting tool call carries a deterministic idempotency key issued by the orchestrator and recorded in the log. When a worker is lost, the call is re-dispatched with the same task id and key; a worker that already ran it reports tool_duplicate instead of running it twice. Exactly-once requires the destination to dedupe on that key.

The alternative, handing the model a failed result and letting it retry, produces a new call at a new step with a new key that no worker can recognise. That is how the side effect happens twice. Norns does not do that.

cost

Tokens are stored per call: input, output, and cache read and write when the provider reports them, with the model that actually served the request. Dollars are not stored. Cost is computed when a run is read, from a rate table operators extend in config, so a price change never rewrites history and a model with no price is reported as unpriced rather than free.

05HTTP API

Runs

Bearer-token authenticated under /api/v1. The full surface is in openapi.yaml; these are the endpoints a client that drives runs needs.

POST /agents/:id/messagessend a message; starts a run, or answers a parked one. Conversational clients never need to switch endpoints.
GET /runs/:idstatus, lineage, waiting_for, cost
GET /runs/:id/eventsthe full log
GET /runs/:id/summaryfixed-size account: verdict, counters, per-tool usage, collapsed timeline, and signals such as loop, retry_storm, unknown_tool, parked_unanswered. A 200-step run with 6.4 MB of events summarises to about 5 KB.
POST /runs/:id/replyanswer a run parked on ask_human
POST /runs/:id/forknew run from the history as it stood after step, optionally with a different model, system prompt, or next message
POST /runs/:id/retryresubmit a failed run
POST /runs/:id/cancelterminal; recorded as a policy failure
GET /toolswhat an agent in this tenant can call right now, with source and schema, plus which workers are connected to serve it
POST /run_webhooksregister a URL that receives a signed POST when a run parks, completes, or fails
POST /hooks/:tokeninbound webhook ingress: a signed external event starts a run
POST /serverless_workersdeclare an asleep worker: its tools and a wake URL

Cron triggers start runs on a schedule. A trigger that fires into a conversation parked on a question is refused as busy and that firing is skipped, so the question stays open.

07Local setup

Orchestrator, scaffold, worker
