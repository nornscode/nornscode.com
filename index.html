The runtime for long-lived agents.

Norns keeps an agent's state in an append-only event log and dispatches one step at a time to workers you run. The orchestrator never calls a model or executes a tool. A run survives the loss of any worker, a deploy, or a restart of the orchestrator itself.

System

Orchestrator and workers

The orchestrator is an Elixir application in front of Postgres. It holds agent definitions, conversations, and the run event log, and runs one BEAM process per live agent, started on the first message and stopped when idle. It decides what happens next and writes it down. It does not hold provider API keys, tool implementations, or a network path to anything the tools reach, and it cannot call a model. Message content is opaque to it: routing is on roles, tool names, ids, steps and usage, never on the text the model sees.

Workers are your code, in your network. A worker connects over a WebSocket, registers its capabilities and the tools it serves with their JSON schemas, and receives task pushes in a provider-neutral format that it translates to Anthropic, OpenAI, or whatever it uses. A worker can also be asleep: a serverless worker declares its tools and a wake URL up front, and the orchestrator POSTs a signed wake when a task arrives for it.

When a worker goes away, the tasks it held are dispatched again to any matching worker, with the same task id and the same idempotency key. With no worker available they queue until one registers. A task that outlives three workers is reported to the agent rather than dispatched a fourth time, since by then it is more likely the cause than the victim.

Agent process

One process per agent, state from the log

Each agent is a GenServer that moves between a small set of states. It is never blocked: it answers status queries in every state, and because the state is derived from the event log rather than held in memory, a process that crashes comes back where it was. A run parked on a question re-parks on the same question. Completed steps are not run again.

Four tools are resolved by the orchestrator itself rather than a worker: wait, ask_human, launch_agent and list_agents. They are the primitives for time, people, and other agents, and they live in the orchestrator because each one is a reason for a run to outlast a process.

Event log

Append-only, versioned, the only source of truth

Every LLM request and response, tool call and result, checkpoint, retry, human question and answer, and sub-agent launch is a validated event in Postgres. Run state is a fold over that table. Resume, fork, cost accounting and the run summary all read from it and nothing else, so there is no second copy of the truth to drift.

Delivery is at-least-once with duplicate suppression. A side-effecting tool call carries a deterministic idempotency key, issued by the orchestrator and recorded in the log. When a worker is lost, the call is dispatched again under the same key, and a worker that already ran it reports a duplicate instead of running it twice. Exactly-once requires the destination to dedupe on that key; the runtime does not pretend otherwise.

Transient failures retry with backoff; rate limits retry longer; validation and policy failures are terminal. Token usage and the serving model are stored per call, and cost is priced when a run is read, so a rate change never rewrites history.
