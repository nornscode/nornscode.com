The runtime for long-lived agents.

Norns keeps an agent's state in an append-only event log and dispatches one step at a time to workers you run. The orchestrator never calls a model or executes a tool. A run survives the loss of any worker, a deploy, or a restart of the orchestrator itself.

System

Orchestrator and workers

The orchestrator is an Elixir application in front of Postgres. It holds agent definitions, conversations, and the run event log, and runs one BEAM process per live agent, started on the first message and stopped when idle. It decides what happens next and writes it down. It does not hold provider API keys, tool implementations, or a network path to anything the tools reach, and it cannot call a model. Message content is opaque to it: routing is on roles, tool names, ids, steps and usage, never on the text the model sees.

Workers are your code, in your network. A worker connects over a WebSocket, registers its capabilities and the tools it serves with their JSON schemas, and receives task pushes in a provider-neutral format that it translates to Anthropic, OpenAI, or whatever it uses. A worker can also be asleep: a serverless worker declares its tools and a wake URL up front, and the orchestrator POSTs a signed wake when a task arrives for it.

When a worker goes away, the tasks it held are dispatched again to any matching worker, with the same task id and the same idempotency key. With no worker available they queue until one registers. A task that outlives three workers is reported to the agent rather than dispatched a fourth time, since by then it is more likely the cause than the victim.

Agent process

States

The process is never blocked. It answers status queries in every state, and the state is derived from the log, so a crashed process comes back in the state it left.

A run parked on a question re-parks on the same question after a restart, because the pause is re-derived from the still pending ask_human call. The run JSON carries status: "waiting" and a waiting_for object, so a client can tell working from waiting without reading the log.

An agent runs in task mode, where each message starts a fresh run with no history, or conversation mode, where messages append to a persistent conversation keyed by an external id such as a Slack thread. One agent serves many conversations concurrently, each in its own process, and a sliding window with a compaction summary bounds context growth.

Four tools are resolved by the orchestrator itself and cannot be shadowed by a worker: wait, ask_human, launch_agent and list_agents. Sub-agent launches are authorized server-side by allowlist and nesting depth, every decision is logged, and a resumed parent reattaches to its in-flight child rather than launching it again. Everything else is a worker tool.

Worker protocol

On the wire

Workers join worker:lobby with a registration and then receive task pushes. The format is provider-neutral; the reference implementations are the Python and Elixir SDKs.

A worker that joined with message_cache keeps the last message list it was sent per run and receives messages_delta: {base_count, drop, append} on later steps instead of the full history. A miss is answered with message_cache_miss and the full list is resent at the same step without counting a retry. Unknown feature names are ignored, so a newer SDK joins an older core.

delivery guarantee

At-least-once with duplicate suppression. A side-effecting tool call carries a deterministic idempotency key issued by the orchestrator and recorded in the log. When a worker is lost, the call is re-dispatched with the same task id and key; a worker that already ran it reports tool_duplicate instead of running it twice. Exactly-once requires the destination to dedupe on that key.

The alternative, handing the model a failed result and letting it retry, produces a new call at a new step with a new key that no worker can recognise. That is how the side effect happens twice. Norns does not do that.

cost

Tokens are stored per call: input, output, and cache read and write when the provider reports them, with the model that actually served the request. Dollars are not stored. Cost is computed when a run is read, from a rate table operators extend in config, so a price change never rewrites history and a model with no price is reported as unpriced rather than free.

HTTP API

Driving a run

Bearer-token authenticated under /api/v1. A client needs five calls; the rest of the surface is in openapi.yaml.

POST /agents/:id/messagessend a message. Starts a run, or answers a parked one.
GET /runs/:idstatus, lineage, waiting_for, cost
GET /runs/:id/eventsthe full log
GET /runs/:id/summarya fixed-size account of the run, with signals such as loop and retry_storm
POST /runs/:id/forka new run from any step, optionally on a different model or system prompt

Run webhooks deliver a signed POST when a run parks, completes, or fails. Cron triggers and inbound webhooks start runs without a client.
