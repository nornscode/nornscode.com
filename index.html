Durable agent runtime.

Norns separates an agent's state from the process that executes it. The orchestrator holds an append-only event log and dispatches one step at a time. Workers in your infrastructure make the LLM calls, run the tools, and hold the keys. A run outlives any worker, deploy, or orchestrator restart.

Install
$ brew install nornscode/tap/nornsctl

Execution model.

The orchestrator is a state machine. It never calls a model and never runs a tool.

01

Orchestrator

Holds

Agent definitions, conversations, and the run event log, in Postgres. Each agent is a BEAM process with four states: idle, awaiting LLM, awaiting tools, waiting on a human.

Does not hold

API keys, tool code, or prompt text it has to read. Message content is opaque to the core; it routes on roles, tool names, ids and steps.

02

Workers

Connect

Over a WebSocket, registering capabilities (llm, tools) and the tools they serve with their input schemas. Tasks are pushed in a provider-neutral format; the worker translates to its LLM provider.

Disconnect

Tasks the worker held are re-dispatched with the same task id and idempotency key. With no worker to take them they queue and flush on the next registration. A worker can also be asleep behind a signed wake URL.

03

Recovery

Resume

Run state is rebuilt from the log, not from a process. On restart, pending tool calls are re-dispatched and a run parked on ask_human re-parks on the same question. Completed steps are not run again.

Guarantee

At-least-once with duplicate suppression. Side-effecting tools carry a deterministic key; a worker that already ran the call reports tool_duplicate instead of running it twice. Exactly-once needs a destination that dedupes on the key.

The event log.

Versioned, validated events: lifecycle, LLM request and response, tool call and result, checkpoint, retry, human question and answer, sub-agent launch. Token usage and the serving model are recorded per call; cost is priced at read time so a rate change never rewrites history.

Read
GET /runs/:id/events is the full log. GET /runs/:id/summary is a fixed-size account of it: verdict, counters, per-tool usage, a collapsed timeline, and signals such as loop, retry_storm, unknown_tool.
Fork
POST /runs/:id/fork starts a new run from any step of an existing one, optionally with a different model, system prompt, or next message.
Retry
POST /runs/:id/retry resubmits a failed run. Transient failures retry on their own: exponential backoff, three attempts; rate limits get ten.
Notify
A run webhook receives a signed POST when a run parks on a question, completes, or fails. Reply to a parked run with POST /runs/:id/reply or by sending the agent its next message.

In production since April.

Mimir is a Slack bot that answers questions about a project from the GitHub repos and pages it is pointed at. Every Slack thread is a Norns run. Between 2026-04-15 and 2026-10-04: 62 threads, 130 runs, 104 redeploys of the runtime and 44 of Mimir. Eleven runs failed, each on a provider or request error recorded in its log. None was lost to a worker going away.
